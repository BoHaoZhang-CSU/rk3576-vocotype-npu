# 踩坑记录

按「会在什么时候绊倒你」分组。每条都是实际踩到的，不是从文档抄的。

---

## A. 环境：动手之前先搞清楚

### A1. NPU 不在 `/dev/rknpu` 上

`ls /dev/rknpu` 什么都没有，很容易以为 NPU 不可用。实际上 RK3576 的 NPU 走的是
**DRM accel 节点**：

```bash
grep -l DRIVER=RKNPU /sys/class/drm/renderD*/device/uevent
# → /sys/class/drm/renderD129/device/uevent
```

设备树节点是 `/npu@27700000`。别被 `ls /dev/rknpu` 误导。

### A2. `onnxoptimizer==0.3.8` 没有 arm64 wheel

源码编译会失败。**但你不需要它** —— 不装不影响 ONNX 转换。
（这是选型阶段想自己转模型时踩的；后来发现官方有现成的 rk3576 模型，压根不用转。）

### A3. opencv-python 会把 numpy 顶到 2.x

rknn-toolkit2 要求 `numpy<=1.26.4`。装 opencv-python 新版时 pip 会顺手把 numpy
升到 2.x，然后 rknn 就报错。**必须钉版本**：`pip install "numpy==1.26.4"`。

### A4. 不能靠 grep wheel 里的 `.py` 判断依赖

想确认某个包是不是必需时，`grep` 包目录里的 `.py` 文件**找不到**
`import torch` / `import cv2` —— 因为那些模块是 Cython 编译进 `.so` 的，
源码里 grep 不到，但运行时确实是硬性 `import`。要判断只能实际跑一遍。

## B. sherpa-onnx + RKNN

### B1. PyPI 上的 sherpa-onnx **不带** RKNN 后端 ⭐

**这是最大的一个坑。** `pip install sherpa-onnx` 装完，`provider="rknn"` 完全走不通。

**怎么确认**（这个判据很好用）：

```bash
so=$(python3 -c "import sherpa_onnx,os;print(os.path.dirname(sherpa_onnx.__file__))")
grep -a "offline-paraformer-model-rknn" $so/lib/_sherpa_onnx*.so
```

有输出 = 带 RKNN 离线 Paraformer；没输出 = 不带。原理：只有开了
`SHERPA_ONNX_ENABLE_RKNN` 才会把 `offline-paraformer-model-rknn.cc` 编进去，
而源文件名会留在扩展模块的字符串表里。

**本机实测**：PyPI 的 1.13.8 没有；从源码编的 1.13.8 有。

**解决**：从源码编（约 25 分钟）。

```bash
git clone --depth 1 -b v1.13.8 https://github.com/k2-fsa/sherpa-onnx
cd sherpa-onnx
SHERPA_ONNX_CMAKE_ARGS="-DSHERPA_ONNX_ENABLE_RKNN=ON" pip install .
```

需要 `/usr/include/rknn_api.h` 和 `librknnrt.so`（Radxa 镜像自带的
`rknpu2-rk3588` 包提供）。仓库自带的 `build-rknn-linux-aarch64.sh` 是**交叉编译**
用的，在板子上直接编**不要用**。没装 ninja 也没关系，cmake 会用 make。

### B2. `--paraformer=` 属于 `sherpa-onnx-offline`，不属于 `sherpa-onnx`

`sherpa-onnx` 是**流式** CLI，`sherpa-onnx-offline` 才是离线的。
我给流式 CLI 传 `--paraformer=` 时它报 `Invalid option`，在这上面绕了一圈。

### B3. 官方预编译模型：rk3588 版在 rk3576 上会被直接拒绝

```
This rknn model is for RK3588, but current platform is RK3576
```

这是**选了错误平台的资产**，不是模型本身的问题。每个平台（rk3562/3566/3568/3576/3588）
的模型都是分开的，看清楚名字里的平台号。

### B4. `airockchip/rknn_model_zoo` 的 zipformer 示例不能用在 sherpa-onnx

那个仓库的 zipformer 示例虽然明写支持 RK3576，但**跟 sherpa-onnx 不兼容**，
sherpa-onnx 官方文档专门警告过。

### B5. 官方那份 rk3576 **流式** zipformer 是坏的 ⭐

同一个 wav（md5 相同）：

| | 结果 |
|---|---|
| 官方 `sherpa-onnx-rk3576-streaming-zipformer-*` | 加载正常、`custom_string` 正常、**不报任何错**，但输出**永远是空字符串** |
| 自己转的 | 正确输出「昨天是 MONDAY …」 |

CLI 和 Python API 都试过，30 秒音频 + beam search 也是空。差别在 chunk 配置：
官方 `T=71;decode_chunk_len=64`，自转的 `T=39;decode_chunk_len=32`。

**结论**：流式要用自转的，官方那份别用。这种事最坑 —— **不报错**，只是结果不对。

### B6. RKNN 不支持 `If` 算子

某个模型的 decoder ONNX 里有 `Shape→Gather→Equal→If`，RKNN 报
`All outputs of model are constants, The model is invalid!`。
静态形状下条件恒为真，所以要**内联 then 分支**。

内联时**必须 `copy.deepcopy` 保留属性** —— 用 `helper.make_node` 重建会丢
`value` 属性。改完一定要用 onnxruntime 对拍验证。

### B7. 改 ONNX 动态维度：先读再清

要先读 `d.dim_param` **再** `ClearField`，否则所有维度都会变成 1。

### B8. 其它几个转换期的坑

- sherpa 的 `GetEncoderInitStates` 要求 encoder 输入类型是 **FP16 或 INT64**，
  float32 会直接退出。rknn-toolkit2 默认 `float_dtype` 就是 fp16，不用改。
- RKNN 会把 4 维 cache 张量自动转成 **NHWC**。sherpa 源码里那段作者自己写着
  「我不理解为什么要这样」的 `ConvertNCHWtoNHWC` 就是为此存在的。
- 官方 Paraformer 转换脚本用的 `optimization_level=0`，**不是**默认的 3。

### B9. RKNN 上下文不是线程安全的

想并行就得**每个线程一个独立的 recognizer**（各自一份模型）。共用一个会出错。
代价是每个实例都要占一份 NPU 内存（见 D1）。

## C. 接进 VocoType

### C1. 不要用 VAD 切长音频 ⭐

模型是固定窗口的，长音频必须切。第一版用 Silero VAD 切，结果：

> 「对我做了介绍啊」→ 被切成三段 → 识别成「对我做了介绍什么？我想说的事呢？」

VAD 会切在词中间，**丢字**。而且每段各付一次窗口钱，更慢。

**改成在能量最低处切成 ≤9.6 秒的块**，又快又准（RTF 0.052）。所以 worker 里
**没有 VAD**。

### C2. 别用 30 秒档整段跑长音频

29 秒音频用 30 秒档一次跑完：前 20 秒正确，后面变成
「就就觉是在特别别就就自自自的的一思」。固定形状模型的**尾巴会糊**。
宁可切块。

### C3. 热词没了

sherpa-onnx 的**离线** Paraformer 没有热词偏置（`hotwords_file` 只对 transducer
生效）。好在核心自己的 `rewrite_terms` 别名替换仍然生效，
「沃口泰普 → VocoType」这类修正照旧。

### C4. 核心 IPC 的两个反直觉行为

写测试客户端必踩：

1. **响应不带换行符。** 不能按行读，要读到 EOF 或者解析成功为止。
2. **每个连接只服务一个请求**就关闭。不能复用连接。

### C5. `asr.idle_timeout_s` 默认只有 300 秒

`config.cpp:113`。worker 空闲超过这个时间就退出，下次说话要重新加载模型，
白等 5 秒。日志里实测踩到过一次（11:22 说完，11:37 再说）。

**改成 3600。** 代价是常驻 2.9 GB 一直占着。

### C6. 流式卡的根因是「默认 1 线程」

`config.cpp:236`：

```cpp
streaming_asr.threads = clamp(value_or<int>(streaming, "intra_op_num_threads", 1), 1, 4);
```

**默认 1 线程**。而 `asr_streaming` 段里本来没这个键（离线段调过，流式段从没调）。

1 线程刚好卡在**实时临界点**：600 ms 音频要算 601 ms，实时余量 1.00×。
跑久了必欠账 → 文字越拖越远 → 就是「卡」的感觉。

改 `"intra_op_num_threads": 4` 后余量 2.7×。详细数据见 `01-实测数据.md` 第 8 节。

## D. NPU 内存

### D1. NPU 内存是**跨进程共享**的有限池 ⭐⭐

最反直觉的一个。普通内存还剩 6.4 GB，NPU 侧却分配不出来：

```
failed to malloc npu memory, size: 333400832
rknn_init, load model failed
```

实测池子上限在 **2.2～2.6 GB**。三个模型实例（1.3 GB NPU 内存）常驻时，
再起第二个 worker 就会在第三个实例上失败。

**真正麻烦的是**：sherpa 的 C++ 层**直接 `exit(255)`**，Python 的 `try/except`
接不住，所以 worker 里的兜底逻辑在这条路径上失效，整个进程死掉，
从 Python 层看像是「莫名其妙就没了」。

**对策**：`parallel_chunks: 1`（省 440 MB）。

**怎么发现的**：`bench_cpu_vs_npu.py` 崩了，一开始以为是并发写错了，
改成串行跑还是崩。单独跑 worker 才看到 exit code 255 和那句 malloc 失败。

## E. fcitx5 补丁（可选）

### E1. `fcitx5 -r -d` 用管道接输出会永不返回

守护进程继承了 stdout，管道一直不关闭，命令挂着不回来。

```bash
setsid fcitx5 -r -d </dev/null >>/tmp/fcitx5.log 2>&1
```

### E2. 改成「按一下切换」必须防自动重复 ⭐

改完之后「正在录音」时收到的**每一次按下**都等于「停止」。但有些前端会把
「按住不放」报成一串 press/release 事件 —— 按久一点就会立刻停录。

加 `TOGGLE_STOP_DEBOUNCE_US = 400000`：开录后 400 ms 内的按下当自动重复丢掉。
**400 ms 比最短录音时长（1000 ms）小**，所以正常点按不受影响。

### E3. 改了上游源码，`git pull` 会覆盖

这是改 `vocotype_module.cpp`，不是配置。以后拉代码或重编译都会把它冲掉，
得重打补丁。补丁在 `patches/`。

## F. 我自己犯过的方法论错误

记下来是为了别重复。

### F1. 拿「单线程 CPU」跟 NPU 比，得出虚高的加速比

一开始算出 1.8×，后来发现是拿 CPU **单线程**比 NPU。公平对比（同模型同时长）：
CPU 1/2/4 线程 RTF = 0.523/0.419/0.395，NPU = 0.291 —— 只快 **1.36×**。

**教训**：报加速比必须写清楚对比的是哪个配置。CPU 多线程是默认状态，
拿单线程当基准是自欺欺人。

### F2. 「官方预编译模型全是 rk3588」——错的

当时只查了 zipformer 就下了结论。实际离线 Paraformer 官方**有** rk3576 版
（`sherpa-onnx-rk3576-{5,10,15,20,25,30}-seconds-paraformer-zh-2023-03-28`）。
**教训**：一个模型没有 ≠ 一类模型都没有。查资产要用命名规律去探：

```bash
curl -sI "https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/<文件名>"
# 302 = 存在，404 = 不存在
```

（顺便：这些 rk3576 离线模型在 GitHub release 里，**不在** HuggingFace。）

### F3. 「librknnrt 2.3.x 有崩溃警告」——也是错的

官方文档只说了「librknnrt 2.2.0 在 rk3588 上已知可用」，
**没有**任何关于 2.3.x 会崩的说法。本机跑的就是 **2.3.0**，一切正常。

**教训**：不要把「文档没提」当成「有问题」。
